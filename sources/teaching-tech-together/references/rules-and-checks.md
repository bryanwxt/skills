Part 2 holds four review checklists (lesson material, a live session, exercises, an online course). ## Part 1 — The core on one page

These are the rules a teaching skill should hold in working memory. Everything else elaborates them.

**Know your learners.** Name the learners concretely: write personas, ask them what they want, and listen. Experts are not their learners, and subject expertise is not teaching skill. (LES-3, LES-5, MEM-18, WHY-1)

**Design backward.** Start from what learners will be able to do, write the summative and formative assessments next, and write only enough content to get from one check to the next. Objectives are single sentences with measurable verbs; introductory courses stay within Bloom's first four levels. (LES-1, LES-8, LES-9, LES-13, LES-14)

**Build mental models, then check them often.** Novices need a correct model, not a pile of facts. Run a formative check every 10–15 minutes. Write MCQ distractors that each diagnose a real misconception, and act on the vote pattern. (MOD-2, MOD-7, MOD-8, MOD-11)

**Mind working memory.** Chunk new material into small pieces. Make connections explicit, using concept maps to decide content. Remove "just" and fill in the steps experts skip. (MEM-1, MEM-3, MEM-5, MEM-8, COG-2)

**Cut extraneous load.** Use worked examples, then fade them, then set problems. Use Parsons problems and labelled subgoals. Avoid split attention, decorative graphics, and narration duplicated as on-screen text. (COG-3, COG-5, COG-6, COG-11 to COG-13, COG-16)

**Teach how to learn.** Teach spaced and retrieval practice, interleaving, elaboration, concrete examples, and dual coding, by name. Promise near transfer, never far. (IND-1, IND-3, IND-6)

**Teach the process, not just the product.** Live-code in small steps and make mistakes in the open. Have learners predict before running code and trace values. Model debugging and testing. Target the known novice misconceptions. (PRF-16, PRF-17, PCK-1, PCK-5, PCK-8, PCK-10, PCK-12)

**Motivate by success.** Teach what is quick to master and immediately useful first. Use authentic tasks with tangible artifacts. Eliminate the demotivators: contempt, tool-bashing, "just", bluffing, and talk of "natural programmers". (MOT-6, MOT-7, MOT-11, MOT-15)

**Include everyone.** Adopt and enforce a Code of Conduct. Prepare accessibility accommodations in advance. Explain under-representation structurally. (WHY-3, MOT-18, MOT-21, MOT-26, CLS-1)

**Use classroom practices that work, but few at a time.** Peer instruction, pair programming, sticky notes, shared notes, and never a blank page all work. Add at most one new technique per short workshop. (CLS-5, CLS-20, CLS-24, CLS-27, CLS-41)

**Improve as a performer.** Record yourself and review the recording, ask for specific feedback, and use the 2×2 grid. (PRF-4, PRF-8, PRF-13)

**Keep online teaching human.** Use short videos paired with activities, frequent deadlines, and small synchronous groups. Never mix one in-room group with remote attendees. (ONL-5, ONL-9, ONL-14, ONL-30)

**Grow a community deliberately.** Join before you found. Give newcomers a ramp and members many ways to contribute. Make power formal and accountable. Run disciplined meetings. (COM-6, COM-4, COM-15, COM-23, COM-30)

**Evidence, with its strength stated.** Don't use learning styles, the learning pyramid, or far transfer. Learner satisfaction is not evidence of learning. (PCK-16, PCK-26, WHY-11)

## Part 2 — Review checklists

Each item is a yes/no question, and a "no" is a finding. Report findings with their rule IDs, the highest-impact ones first.

### A. Lesson or course material
- [ ] Are the learners named as personas, and do the lesson's reasons match theirs? (LES-3, WHY-7)
- [ ] Is every objective one sentence, describing learner performance with a measurable verb, at an appropriate Bloom level? (LES-13, LES-14)
- [ ] Were the assessments written before the content, and does each section lead to one? (LES-1, LES-9)
- [ ] Is there a formative check about every 10–15 minutes? (MOD-7, LES-8)
- [ ] Does each MCQ distractor map to a specific misconception, with no joke options? (MOD-8, MOD-10)
- [ ] Are the "just"s and skipped steps gone? Are explanations ordered by what learners already know? (MEM-1 to MEM-3)
- [ ] Is new content per step small, and are concepts explicitly connected? (COG-2, COG-4, MEM-5)
- [ ] Do worked examples come before independent problems, with fading in between? (COG-5, COG-6)
- [ ] Is there no split attention, decorative graphics, or duplicated narration? (COG-13, COG-16)
- [ ] Is quick, useful content first, with authentic tasks and real data rather than `foo`/`bar`? (MOT-6 to MOT-8)
- [ ] Is it free of demotivators and stereotype phrases? (MOT-11, MOT-15, MOT-27)
- [ ] Does it pass the accessibility checklist: real headings, no colour-only meaning, code as text, narrated video? (MOT-20, `10` T3)
- [ ] For programming: does it show process, debugging, prediction, and tracing; target known misconceptions; and use one consistent, linted style? (PCK-1, PCK-5, PCK-8, PCK-9, PCK-12, PCK-20)
- [ ] Is it free of debunked claims? (PCK-26)
- [ ] Is it maintainable: documented, built from small remixable pieces, and openly licensed? (LES-19, LES-20, WHY-10)

### B. A live session (observation)
- [ ] Is the Code of Conduct stated, and was any incident handled by severity, in front of witnesses, and reported? (WHY-3, CLS-1 to CLS-4)
- [ ] Did the introductions convey both competence and approachability? (CLS-31)
- [ ] Was code live-coded rather than shown on slides, with narration, small steps, and mistakes diagnosed aloud? (PRF-16, PRF-17, PRF-19, PRF-29)
- [ ] Were learners asked to predict before code was run? (PRF-18, CLS-37)
- [ ] Was the screen readable from the back row, notifications off, and the environment matching the learners'? (PRF-21, PRF-22, PRF-26)
- [ ] Were there regular formative checks, or peer instruction with a public first vote? (MOD-7, CLS-5, CLS-6)
- [ ] Were sticky-note status flags, pairing with role switches, and shared notes used? (CLS-20, CLS-22, CLS-24)
- [ ] Did the teacher stay off learners' keyboards and repeat questions before answering? (CLS-34, CLS-35)
- [ ] Did the co-teachers follow an explicit model, with no interruptions? (CLS-7, CLS-10, CLS-11)
- [ ] Was feedback collected (minute cards, one up / one down) and acted on? (CLS-26, CLS-36)
- [ ] Was innovation limited? (CLS-41)

### C. An exercise or assessment
- [ ] Is the type chosen for what it assesses? (EXR-1, `12` catalog)
- [ ] Does the novice start from a non-blank page: fill-in-the-blanks, a Parsons problem, or starter code without boilerplate? (EXR-7, CLS-27)
- [ ] Novice Parsons problem: no distractor lines? (EXR-8)
- [ ] Tracing: free-entry answers in a variables-by-lines table? (EXR-9, EXR-10)
- [ ] Code and run: brief, with only 1–2 valid answers and a named function? (EXR-3)
- [ ] Auto-graded: public tests, correct-but-different code accepted, actionable messages, and expected outputs hidden? (EXR-4, EXR-19, EXR-23, EXR-24)
- [ ] Peer-graded: a rubric of observable behaviours, with calibration? (IND-25, IND-26, EXR-26)
- [ ] Is the time estimate realistic, and was it piloted on a colleague? (EXR-28, EXR-29)

### D. An online course or video
- [ ] Is the choice between online-with-humans and automated deliberate? (ONL-1, ONL-2)
- [ ] Are videos six minutes or less, each paired with an activity? (ONL-9, ONL-14)
- [ ] Is video used to engage or show actions, with explanations in text, and misconceptions stated and refuted? (ONL-10, ONL-17)
- [ ] Are deadlines frequent and enforced, with weekly small-group synchronous sessions? (ONL-4, ONL-5)
- [ ] Is there instructor presence, peer interaction, and an enforced code of conduct? (ONL-7, ONL-20, ONL-22)
- [ ] Is hybrid delivery all-remote with local helpers? (ONL-30)
- [ ] Was learner privacy weighed before collecting analytics? (ONL-31)

### MOD — Building Mental Models (`02-mental-models.md`)

- **MOD-1** — Decide early who a lesson is for (novice, competent practitioner or expert) and write it as a tutorial or a manual accordingly. — Ch 2 intro
- **MOD-2** — For novices, teach the concepts that organize the facts before or alongside the facts themselves. Don't present a pile of facts. — Ch 2 intro
- **MOD-3** — Present common misconceptions explicitly alongside the correct concept. — Ch 2 intro

- **MOD-6** — Use formative assessment throughout every lesson, and make each check quick and its result clear. — §2.1

- **MOD-9** — Source distractors from real learner errors: past learners' questions and problems, your own and colleagues' misconceptions, the field's historical misunderstandings, open-ended questions asked in earlier classes, and Q&A sites. — §2.1

- **MOD-12** — Make sure formative assessments prepare learners for the summative assessment. Never examine what the teaching didn't prepare learners for. If an exam includes novel problems, give practice and feedback on novel problems first. — §2.1
- **MOD-13** — Use a preemptive check at the start of a topic and skip material the class already knows. — §2.1
- **MOD-14** — Collect answers simultaneously (coloured or numbered cards), offer an "I have no idea" option, and allow a few seconds of neighbour discussion before answering. — §2.1
- **MOD-15** — Use other quick, unambiguous formats where MCQs don't fit: Parsons Problems, matching problems, or 2–5-word short answers. — §2.1
- **MOD-16** — Write formative assessments as a design exercise even if you won't use them in class. — §2.1

### PCK — Pedagogical Content Knowledge for Programming (`07-programming-pck.md`)

- **PCK-1** — Show learners *how* to program: demonstrate the process, not just the language features. — §7.1
- **PCK-2** — When demonstrating, take small steps with frequent feedback, and pick a plan and stick to it. — §7.1
- **PCK-3** — Show the expert writing order explicitly: signature first, then control flow, then initialization and corner cases. — §7.1
- **PCK-4** — Give novices a vocabulary of programming plans, e.g. label variables with their roles (stepper, gatherer, most-wanted holder…). — §7.1
- **PCK-5** — Teach debugging explicitly as a skill: stepping with a debugger, hand tracing, writing tests, and re-reading the spec. Deliberately commit and correct typical bad habits (the same print in both branches; commenting out correct lines). — §7.2
- **PCK-6** — Teach slower learners the strategies faster learners use. — §7.2
- **PCK-7** — Teach code reading as the main bug-finding method, using a code-quality rubric introduced in chunks. — §7.2
- **PCK-8** — Before running code in class, have learners predict its output. — §7.2
- **PCK-9** — Teach learners to trace variables' values by writing each new value next to the variable's name as it changes. Have them construct visualizations, not just watch them. — §7.2, §7.7
- **PCK-10** — Teach testing as a way to *find* bugs, not just confirm the happy path. Consider specifying problems as tests to pass (§12.1). Be honest about whether you practise what you preach. — §7.2
- **PCK-11** — Explicitly teach that computers don't understand programs or intentions (the "superbug"). — §7.3
- **PCK-12** — Target known misconceptions with diagnostic exercises: spreadsheet-style variables, variables remembering history, same-id-means-same-object, functions running when defined, constantly re-evaluated loop or if conditions, assignment moving values, and the [Sirk2012] list. — §7.3, §7.9
- **PCK-13** — Prioritize errors by measured frequency, not teacher intuition, and distinguish unfinished code from mistakes. — §7.4
- **PCK-14** — Never dismiss syntax as "simple". Expect basic syntax errors (mismatched quotes and brackets, tag syntax) to persist for weeks, and teach them explicitly. — §7.4
- **PCK-15** — Sequence topics by conceptual dependency, using published trajectories where they exist (e.g. variables → operators → precedence; the conditionals trajectory). — §7.5
- **PCK-16** — Measure and track learning in ways comparable over time. Don't use teaching evaluations as evidence of learning. — §7.5
- **PCK-17** — Start children and teens with blocks-based tools before moving to text. For adults, expect resistance to childish-looking tools. — §7.6
- **PCK-18** — Start with procedural programming. Delay defining classes and higher-order functions until learners grasp basic control structures and data types, and adjust timing to learners' goals (e.g. JavaScript callbacks early for web apps). — §7.6
- **PCK-19** — Don't claim research settles typed vs. untyped languages for novices. — §7.6
- **PCK-20** — Use one consistent naming and code style in all examples, enforced by a style-checking tool (e.g. PEP 8 for Python). Prefer full-word names. — §7.6
- **PCK-21** — Give learners deliberate practice reading and interpreting error messages, and use enhanced, novice-friendly messages where tools allow. — §7.7
- **PCK-22** — When comparing graphical and textual representations (e.g. flowcharts vs. pseudocode), make both equally well structured. — §7.7
- **PCK-23** — Favour interventions with the strongest reported effects: media computation, group work, cooperative learning, CS0 bridging, contextualization, peer support. Don't count on a game theme alone. — §7.8
- **PCK-24** — Include non-coding ("unplugged") computational creativity exercises, e.g. describing everyday objects by inputs, outputs, and functions. — §7.8
- **PCK-25** — Make an explicit notional machine a learning objective, introduce it piece by piece, and reuse it whenever you draw pictures or trace execution. — Theory appendix
- **PCK-26** — Don't design lessons around debunked myths: VAK learning styles, the learning pyramid percentages, brain games. — Theory appendix
