# Structuring the Analysis of the Problem

> Source: Minto, *The Minto Pyramid Principle*, Ch. 9 "Structuring the Analysis of the Problem", book pp. 140–167 (pp. 164–167 are bound out of order in the scanned PDF). Paraphrased reference; rule IDs use prefix `ANL`.

## When a skill needs this
- Planning a consulting study, research project or investigation: deciding what data to gather and why, before gathering it.
- Building a diagnostic tree (physical, financial, task, activity, classification or choice structure) to find the causes of an undesired result.
- Generating a mutually exclusive, collectively exhaustive (MECE) set of possible solutions or strategic options, then choosing among them.
- Reviewing a proposal's "Key Issues" / "Major Issues" list, or any grouped list, for logical flaws, irrelevance and gaps.
- Turning analytical structures into the Key Line and supporting points of a report or proposal pyramid.

## Key terms
| Term | Meaning (one line) |
|---|---|
| Standard analysis flow | Gather data → state findings → draw conclusions → recommend actions. |
| Data-first analysis | Collecting whatever data exists and postponing thought until it is all in; Minto's foil. |
| Company/industry analysis | The 1950s–60s default consulting approach: key success factors, client strengths, comparison, recommendations. |
| Scientific method (classic) | Generate alternative hypotheses → devise crucial experiments → run them for a clean result → plan action. |
| Crucial experiment | A test whose outcomes each exclude one or more hypotheses. |
| Diagnostic framework | A picture of the structure where the problem arose, used to find causes via yes/no questions. |
| Logic tree (nondiagnostic) | A MECE breakdown of possible actions or opportunities, used to generate solutions or to test groupings. |
| Three ways to structure | Divide (physical structure), trace cause and effect, classify. |
| Physical structure | Units organized into a system performing a function (e.g., distribution chain, industry value chain). |
| Financial structure | Tree breaking a financial result (e.g., ROI) into its contributing elements. |
| Task structure | Financial tree restated as managerial tasks (Increase…, Reduce…), starting from EPS. |
| Activity structure | Tree tracing every activity or cause that could produce an undesirable effect. |
| Classification of causes | Pre-grouping likely culprits by similarity under a MECE top branch. |
| Choice structure | Tree of successive dual (either/or) choices mirroring a sequential process. |
| Sequential marketing structure | Holland's complete, ordered brand diagnostic: problem? where? why (positioning → distribution → awareness → trial → repurchase)? |
| Yes/no question | Question whose answer unambiguously identifies or excludes a cause; the analytic counterpart of a crucial experiment. |
| Decision tree / PERT diagram | Action-planning charts (choices under uncertainty; activity sequencing); not diagnostic. |
| Issue | Strictly, a question phrased to demand a yes-or-no answer (from the legal "at issue"). |
| Concern | Minto's proposed word for a topic that worries the client but is not a yes/no question. |
| Issue Analysis | Term coined at McKinsey (Hertz and Bales, 1960s NYC) for a decision-analysis technique; now used loosely for almost any tree. |
| Major Decision Variable (MDV) | In original Issue Analysis, a factor at a stage of the policy system that drives performance against objectives. |

## Concepts

### Chapter opening (p. 140)
- Analysis normally runs: gather data → state findings → draw conclusions → recommend actions.
- *Efficiency* depends on designing the fact-finding up front, so the findings that come back already hang together logically.
- Most people do the reverse. They sweep up every available datum in the area and defer serious thought until the whole pile is assembled. It can be done, but it always costs extra effort.
- Minto's alternative: build **diagnostic frameworks and logic trees** first and let them steer both the analysis and the thinking. The problem solving goes faster, *and* the later job of shaping results into a pyramid gets far easier.
- Because data-first is so common, Minto first explains where it came from, then the alternative.

### Starting with the Data (pp. 141–142)
- **History.** Data-first has a respectable origin in early consulting (1950s–60s). The profession was young and firms had not yet built deep knowledge of industries and companies. So every engagement, whatever the problem, began with a full company/industry analysis:
  1. Work out what it takes to succeed in the industry: the market, the economics of price, cost and investment, technology requirements, and how the industry is structured and how profitable it is.
  2. Rate the client on the same ground: market position and sales, technology, economic structure, financial and cost performance.
  3. Measure the client against those success factors.
  4. Recommend concrete moves to seize opportunities and fix problems.
- **Results:**
  - Facts piled up so fast that meaningful conclusions were hard to draw. A leading firm reckoned that roughly **60% of the effort it spent finding and analysing facts went to waste**.
  - Consultants produced many "interesting" facts and exhibits only loosely tied to what turned out to be the real problem.
  - Information was often incomplete, so major recommendations had little or no supporting data. That forced costly, stressful last-minute data hunts.
- **Even with complete data, writing was a huge effort.**
  - Facts were first grouped under headings like Operations, Marketing, Growth Projections, Issues. Ch 7 shows how hard it is to draw conclusions from such groupings.
  - Firms then fell back on presenting material in the order it was gathered, under Findings / Conclusions / Recommendations. Those headings force no more thinking than random topics do.
  - The result: vast writing time and long, dull documents that poorly reflected the insight in the work.
- **The fix the better firms adopted:** structure the analysis of the problem **before** gathering any data. This roughly replicates the classic scientific method:
  1. Propose several competing hypotheses.
  2. Design one or more decisive ("crucial") experiments whose possible outcomes would each rule out at least one hypothesis.
  3. Run them cleanly enough to get an unambiguous result.
  4. Decide the corrective action in light of what was found.
- In practice this means thinking up the likely reasons for the problem and focusing data gathering on proving them right or wrong. Minto calls this Abduction (Appendix A; see `09-abduction.md`). Once confident of the causes, you are well placed to recommend creative solutions.
- **Where the "likely reasons" come from.** They are not pulled from the air. They come from a critical look at how the problem area is organized, i.e., the Opening Scene of the problem definition (`07-defining-the-problem.md`). Getting at that organization in depth calls for a suitable **diagnostic framework**.
- **Two kinds of aid.** There are diagnostic frameworks (to find causes) and nondiagnostic logic trees (to generate recommendations). The two are often lumped together as "analytical techniques" or "Issue Analysis". Keeping them apart means each gets applied where it fits.

### Devising Diagnostic Frameworks (p. 143)
- Purpose: visualize what is going on in the area where the problem occurred. The picture reveals the elements or activities the analysis should focus on.
- **Headache example** (credited to an Andersen Consulting internal presentation). Picture a headache with no known cause, which leaves you unable to pick a remedy. Step one is to visualize possible causes with a MECE classification:
  ```
  Head hurts
    ├─ Physical
    │    ├─ External: bumped/bruised head · allergies · bad-weather sinus headache
    │    └─ Internal: flu/cold · brain tumor · water on the brain
    └─ Mental: stress/tension · hypochondria
  ```
- With the causes laid out, **assess them in order of how easy they are to eliminate**. You don't book a brain-tumor test if it turns out to be a sinus headache.
- **Three ways to structure anything** (Minto attributes this to Ch 6): divide, trace cause and effect, or classify. A diagnostic framework uses one or more of them. The following subsections take each in turn.

### Showing Physical Structure (pp. 143–144)
- The tangible parts of a company or sector are plainly structured: components arranged into systems that each serve some purpose.
- Sketch that system in its actual (or intended) working state. The sketch shows which yes/no questions will expose the causes.
- **Exhibit 37, operation's physical structure:**
  - Chain: Manufacturer → (wholesale distribution) → Wholesaler → (retail distribution) → Retailer → (consumer purchase) → Consumer, with share of market at the consumer.
  - From the Retailer, a MARKETING path (Awareness → Initial purchase → Repurchase) and a SALES path (Shelving → Pricing → Special merchandise support) both lead to the consumer.
  - Use: if share of market is down (R1), ask whether the retailer is failing to build awareness, failing to win the purchase, and so on.
- **Exhibit 38, industry structure:**
  - Chain: Raw material source → Manufacturer → Warehouse distribution → Consumer purchaser → Consumer user → Post-purchase services.
  - Above the chain, economic points of leverage: totally integrated production; long margins; relatively fixed cost of sales coverage.
  - Below the chain, market points of leverage: controlling position with scarce resources; dominant part of wholesale business; significant product advantages; exceptional service capability.
  - Typical early-study use: understand the industry's business process and key trends to spot danger areas.
    1. Segment the industry and find volume and competitive structure for each segment.
    2. Map, per segment, the value added, the cost behaviour, the profit pools and their sensitivity, and the asset commitments.
    3. Look for points of leverage, and gather data from those to find where the business is vulnerable.

### Tracing Cause and Effect (pp. 145–148)
Trace the cause-and-effect elements, activities or tasks that combine to produce an end result. There are three variants.

**1. Financial Structure (Exhibit 39, p. 145).** Used, say, to find the reasons for an R1 of low return on investment.
```
Return on investment
├─ Trading Profit
│   ├─ Sales
│   │   ├─ Prices: estimating accuracy · competitive prices · product costs
│   │   ├─ Products: quality · design · range
│   │   ├─ Service: technical support · reps' effectiveness · delivery
│   │   └─ Market conditions: home market · export market · competition
│   └─ Costs
│       ├─ Variable
│       │   ├─ Labor: cost/hour (rates, overtime) · productivity (methods, turnover) · efficiency (work methods)
│       │   ├─ Services: fuel · power, etc.
│       │   └─ Materials: raw materials (purchase price, quality, wastage) · supplies
│       └─ Fixed: research · selling · maintenance · works
└─ Assets
    ├─ Net current: stocks · debtors · cash · current liabilities
    └─ Fixed: buildings · plant and equipment
```
- Put numbers on the chart, and you quickly see whether the problem is sales down versus last year, costs up, or both.
- Break each element into its key influences, then each influence into components. For example, sales volume depends on product quality, design and range.
- Once the structure is complete, ask questions such as "Is the problem in product volume? In pricing?" Then work out the data needed to answer each **yes or no**.

**2. Task Structure (Exhibit 40, pp. 146–147).** A deeper, more explicit version: the tree shows the important tasks the business must organize itself to perform.
- Start with EPS. Split it following the firm's financial makeup, wording every element as its own **managerial task**. Then lay the P&L account and the balance sheet onto the structure, again phrased as tasks.
- Advantage: if the problem is found at a node, the node already names the kind of action needed.
- Cigarette company example: contribution = revenue − specification costs (leaf, packing materials, duty, direct labor) − advertising & promotion. These become tasks (Increase Net Sales, Reduce Leaf, etc.).
- Once the business's key tasks are known, analyse the numbers in the tree (trends, sensitivities, comparisons with industry and competitors) to set priorities for raising EPS.
```
Increase EPS
├─ Increase Trading Profits and Trading Assets
│   ├─ Increase Tobacco Trading Profits / Trading Assets
│   │   └─ Increase Contribution (for individual brands)
│   │        Revenue → Increase Net Sales
│   │        Less specification cost → Reduce Leaf · Reduce Packing Materials · Reduce Duty · Reduce Direct Labor · Reduce Gift Scheme
│   │        (→ Increase Gross Margin)
│   │        Less advertising & promotion → Reduce Advertising and Promotion   (→ Increase Contribution)
│   ├─ Increase Non-Tobacco Trading Profits / Trading Assets
│   ├─ Reduce Oncost and Overheads (company as a whole, reduce in total)
│   │        Redirect Indirect Labor · Reduce Materials · Reduce Bought Out · Reduce Salaries · Reduce Rent ·
│   │        Reduce Depreciation · Reduce Miscellaneous · Reduce Total Oncost and Overhead
│   └─ Reduce Trading Assets (company as a whole, reduce/minimize)
│            Reduce Plant · Reduce Building and Land · Reduce Stocks · Reduce Work in Progress ·
│            Reduce Finished Goods · Reduce Receivables · Increase Payables · Reduce Cash · Increase Investments
└─ Increase Financial Gearing
    ├─ Increase Interest Received / Reduce Interest Paid → Reduce Interest Paid · Increase Profit
    ├─ Reduce Tax Charge → Increase Net Profit
    └─ Sell or Lease Back Assets → (balance-sheet reductions)
[Right-hand columns group the leaf tasks as P&L-statement categories vs balance-sheet categories.]
```

**3. Activity Structure (Exhibit 41, pp. 147–148).** A tree tracing the activities that produce an undesirable end, such as high costs or overlong installation times.
- **The trick:** visualize *all* the causes that could possibly produce the effect, and place them at their proper levels.
- Example: installing telephone switching equipment. Part of the work is done in the contractor's factory and part on site. On-site elements are the installers, their facilities, the equipment, the testers, and the customer who approves stages. How do these relate?
- Method:
  1. Put the bad outcome at the root (installs overrun their expected duration).
  2. One level down, **hypothesize the MECE reasons**: fewer installers per rack, more man-hours per rack, fewer hours on duty per week.
  3. Break each reason down. Extra man-hours per rack could mean a slower pace, *or* a more demanding job, *or* unplanned delays.
  4. For each, keep asking what could bring it about.
- The outcome is an exhaustive map of the places where fact-gathering and analysis could occur. Industry experience tells you where to look first.
```
Installs overrun expected time
├─ Fewer hours on duty/week
├─ Fewer men/rack on site
└─ More man-hours/rack on site
    ├─ Slower work pace
    │    ├─ Fewer incentives: cash · tenure · promotion
    │    ├─ Lower output expected: longer task standard times · union output restrictions
    │    ├─ Poorer supervision: fewer supervision hours/supervisor · fewer supervisors/man · less skill/supervisor
    │    ├─ Less skilled work force: lower tenure · younger workers · less training/man/year · less specialization
    │    ├─ Poorer working instructions
    │    └─ Poorer tools
    ├─ More time required on site
    │    ├─ Less work done in factory
    │    ├─ More difficult work environment: equipment diversity · storage · access · working-space limits · environmental problems (e.g., dust)
    │    ├─ More tasks required to complete job: more resting time · poorer planning · duplicated work from errors
    │    └─ More stringent installation specs
    └─ Unexpected delays experienced
         ├─ Procedural delays · late changes in plans · poor sequencing/timing of tasks
         ├─ Manpower used elsewhere at short notice
         └─ Waiting for correct external inputs: incorrect / inadequate / late × facilities / equipment / testers
```

### Classifying Possible Causes (pp. 149–152)
- **Classification.** Sort the suspects into families of like causes in advance. The bet is that this early sorting will make it easier to synthesize the facts later.
- **Exhibit 42, possible causes of low profits:**
  ```
  Profits
  ├─ Sales
  │   ├─ Semi-fixed factors: falling market · store number/location · store size · store accessibility
  │   └─ Variable factors (each "wrong"): goods · layout · price · in-store display & facilities ·
  │                        sales staff · advertising outside the store
  ├─ Gross margin on sales: price too low · buying cost too high · wrong mix of goods
  └─ Costs on sales: overelaborate cost base · poor cost control · cost-related merchandise decisions
  ```
  - A sales decline may stem from semi-fixed or from variable factors. Assume both are implicated, then decide what information would prove, for example, (a) a falling market for these goods caused the drop, (b) store coverage doesn't match the market, (c) store size limits volume.
  - **The trick:** make the *upper* branch a MECE classification, as a guide to generating causes lower down. Then write yes/no questions that identify or eliminate each cause.
- **Choice structure (Exhibit 43).** Like the activity structure, it seeks the causes of an undesirable effect. Here, though, each node splits into **two either/or options**, and the splitting continues until the probable causes come into sharper focus.
  ```
  Ineffective sales support
  ├─ Ineffective at headquarters  ✗
  └─ Ineffective at retail
      ├─ Wrong stores  ✗ (that is the problem)
      └─ Right stores
          ├─ Wrong frequency  ✗
          └─ Right frequency
              ├─ Wrong activities  ✗
              └─ Right activities
                  ├─ Effective activities
                  └─ Ineffective activities → priorities not clear · salesman overloaded · wrong compensation · inadequate supervision
  ```
  - **The secret:** picture the sequential selling process (pick the store, call on it, do the right things there, do them well or poorly) and mirror it in the forks. The result shows which analyses must be done, and they in turn show how to solve the problem.
- **Sequential marketing structure (Exhibit 44)**, a more sophisticated choice structure, credited to B. Robert Holland. Its value is its completeness *and* the order in which each element is to be analysed.
  ```
  1 Does the brand have a problem?  total contribution · contribution rate · brand volume · selling price ·
                                     total market volume · discretionary cost · brand market share · non-discretionary cost
  2 Where does the problem lie?      region · channel · pack size · consumer type
  3 Why does the problem exist? → evaluated left to right:
     POSITIONING (properly positioned for the market?) target market · consumer benefit · product spec · selling price · brand name · packaging
     → DISTRIBUTION (made available?) region · channel · account type · pack size · sales-force coverage · sales-force direction · trade terms
     → AWARENESS (target market aware?) attribute awareness · advertising recall · advertising spending rate · media mix · regional weight · advertising communication
     → TRIAL (target market induced to try?) pack · display · promotion type · promotion timing · sell-in effectiveness
     → REPURCHASE (persuaded to repurchase?) product rejection · price/value rejection · frequency of use · occasion of use · consumer profile
  FEEDBACK: if no line of inquiry reveals the problem source, go back and check whether target market and consumer benefit were accurately defined.
  ```
  - Ordering rule: **weaknesses on the left must be fixed before those on the right.** Suppose the analysis finds wrong packaging, misdirected advertising, sloppy promotion and infrequent use by buyers. There is no point coaxing more frequent use before promotion is sorted out, and no point spending on promotion while advertising to the wrong people.
- **Frameworks as explanatory vehicles.** A finished diagnostic framework is a powerful way to walk the client through what is happening in their organization, both factually and conceptually. Three views are possible:
  1. *Current state:* the system as it now operates, producing R1.
  2. *Implied state:* what the system must logically have been doing to yield the R1 observed.
  3. *Ideal state:* the system as it would need to be to yield R2.
  - Views 1 and 2 make the case for change by contrast with the ideal. View 3 surfaces weaknesses by laying the real system against the ideal one.
- **The central point: yes/no questions.** They are the analyst's version of the scientist's crucial experiments: each answer pins down or rules out a contributing cause without ambiguity. A further benefit is that you know beforehand at what point the research is complete.
- **Distinct from decision trees and PERT charts.** Those reveal the *need for action* rather than generating questions. Exhibit 45 shows both:
  - a decision tree (from John F. Magee, *Harvard Business Review*, 1964) choosing between building a big or small plant under high/low demand chance events, with a later expand/no-change decision;
  - a PERT diagram sequencing building tasks (partitions, window frames, plumber's and carpenter's fittings, internal painting, floor finish).

### Applying the Frameworks (pp. 153–156)
- **Common question:** how do I know which framework to build when, and whether to dig into all of it or only parts?
- **Answer, part 1: subject knowledge.** The answer turns on your command of the domain. Problem solving can't succeed without real domain knowledge. You need thorough grounding in the relevant field (manufacturing, marketing, information systems, etc.), and nothing replaces deep, readily available knowledge of the area where the trouble began.
- **Answer, part 2: the Opening Scene.** The Opening Scene usually **points to which frameworks you need**.
- **Exhibit 46, Barrows proposal (heading: ISD can't keep up with growth opportunities):**
  - *Opening Scene:* Barrows org chart with the Information Systems Division (ISD) as one unit. A young, booming business expanding beyond forecast, running new systems that fall somewhat short in four areas: master production planning/scheduling; material planning/control; shop paperwork/floor control; order-status/backlog reporting.
  - *Disturbing Event:* parts shortages; late order fulfilment.
  - *R1:* fear of missing growth opportunities; fear that the systems are under-used (users may not grasp them; support-group productivity is doubtful); no way to tell where the inefficiencies are.
  - *R2:* enough production capability for the forecast growth; support groups that are more efficient and productive.
  - *Consultant's proposed steps:* establish information needs; review existing systems and procedures; propose quick-win changes; find long-term productivity gains; find immediate control gains.

**The Client's Problem (p. 154)**
- ISD's business was growing faster than expected (a rare complaint). Yet despite new production planning and control systems it was slipping on orders and risked missing growth. Barrows suspected users didn't understand the new systems and knew support groups were far from fully productive. It wanted production capability brought to full efficiency and support-group productivity improved.
- **Inference:** since the shortfall is in shop-floor efficiency and output, its roots must be in shop-floor activities and processes. So the first framework should depict those.
- **What the consultant actually planned** was broad, unstructured collection across eight areas: growth forecasts; the division's management goals; information and management requirements; existing systems and procedures; where inefficiency arises and why productivity is low; why control is weak; inventory accuracy (book vs physical); current resources and their use.
- **Data-first risk:** interviewing people on each area would bring back huge amounts of data to organize, synthesize and analyse. The consultant couldn't absorb it all and would lack any simple, objective test of relevance.
- **The alternative:**
  1. First gather only the data needed to build a diagnostic framework of the structure and interactions of current operations.
  2. Examine it knowledgeably and make good guesses (hypotheses) about the probable causes.
  3. Then gather only the information that proves or disproves those guesses.

**The Approach to Analysis (pp. 155–156)**
- **Exhibit 47, partial flow diagram of the system:**
  - Functions: Engineering and Purchasing at top; Order processing, Manufacturing engineering, Material control, Schedules, Dispatching, Operations evaluation in the middle.
  - Numbered information/rule sets: (1) information on order and lead times; (2) bills of material and routings; (3) inventory and ordering factors; (4) master operations and load formulas; (5) shop dispatching and priority rules; control standards; (6) evaluation data for management decisions.
- With the diagram as reference, the consultant can guess where weaknesses probably are and state exactly what a weakness would look like if present. The data questions then follow:
  1. *Order and lead times:* are quoted lead times uncompetitive, and are they met?
  2. *Purchased items:* does sourcing materials, parts or sub-assemblies involve delay or excess cost?
  3. *Stock availability:* do shortages or stock-outs cost sales or add cost?
  4. *Capacity:* will capacity cover forecast demand?
  5. *System costs:* do controls in one area unbalance the system and push costs up elsewhere?
  6. *Management reports:* do status and labor-efficiency reports give adequate control?
- **Planning the data effort.** For each question ask: what must I find out to answer it yes or no?
  - Much of the original list will still be needed. The exceptions are the existing-systems and current-resources items, which will already have been used to draw the diagram. (The book refers here to "Exhibit 46"; the flow diagram is Exhibit 47.)
  - What changes is that the consultant knows beforehand why each item is wanted, and can spot gaps where extra data will be needed.
- **Administrative bonus.** Before fieldwork, every data item can be given a source, an owner, a schedule and a cost estimate. The effort should reach the causes quickly and efficiently and allow suitable, even creative, recommendations.
- **Creativity caveat.** Truly creative remedies will always come mainly from people immersed in the field, whose depth lets them see options that pure logic would not reveal. Those lacking that depth can lean on logic trees to help produce candidate solutions.

### Developing Logic Trees (pp. 156–157)
- Logic trees help generate alternative ways to solve a problem.
- In Sequential Analysis terms (see `07-defining-the-problem.md`):
  - Steps 2–3 (location and cause) **represent the existing system**. Flow diagrams and cause-and-effect trees show how its elements, activities or tasks interlock.
  - Steps 4–5 (what could / should we do) **look the other way**: a logic tree generates possible solutions and their likely impact on the company.
- Logic trees can also **reveal flaws in grouped ideas** once a document is written.

### Generating Possible Solutions (pp. 157–158)
- Logic trees spell out the logically possible actions that could solve a problem.
- **Exhibit 48, ways to cut labor cost.** Returning to the task structure (Exhibit 40), labor cost was found too high. The consultant broke down, systematically and MECE, the possibilities for cutting it:
  1. Break direct labor cost into its elements: primary preparation process; cigarette making department; packing department; other.
  2. Split making-department cost per cigarette into cost per hour × hours per million cigarettes, since (cost/hour) × (hours/cigarettes) = cost/cigarette.
  3. Ways to cut cost per hour: minimize overtime; use cheaper labor; minimize wage awards.
  4. Ways to cut hours per million cigarettes: fewer people per machine; higher machine speeds; higher machine efficiency.
  5. Continue to the next level.
  - The text calls this *indirect* labor; the exhibit's root is "Reduce direct labor costs".
- With the possibilities laid out, the consultant **calculates the benefit and estimates the risk** of each action to arrive at the recommended final set.
- **Exhibit 49, strategic opportunities.** The same approach lays out growth opportunities (for a financial institution in a small European country) and what each would require. Again, aim to be as collectively exhaustive as possible.
  ```
  Exploit openings created by ordinary economic growth
  ├─ Close gaps in today's business
  │    ├─ Lend more to under-served market sectors
  │    ├─ Take a bigger part in public-sector finance
  │    └─ Grow Acceptance Credit lending
  ├─ Serve corporates' growing financial sophistication
  ├─ Fund building & construction expansion
  │    ├─ Commit more finance to construction firms
  │    ├─ Finance land banks
  │    └─ Offer complete financing packages for new housing schemes
  ├─ Benefit from rising EC trade & investment
  └─ Join the increasing flow of foreign-sponsored local projects
       ├─ Do more business with their subsidiaries
       └─ Offer trade finance and FX services
  ```

### Revealing Flaws in Grouped Ideas (pp. 159–162)
- The same technique of displaying logical relationships among groups of activities can be turned on what you have *written*, to test its logic.
- **Texas example, the setting.** A pipes-and-fittings distributor buys from suppliers and stocks a central warehouse, which feeds about a dozen regional warehouses. New owners think the central warehouse's $27 million inventory cost is too high. Because the central warehouse is often out of stock, the regional warehouses also order directly from suppliers, raising inventory further.
- **The proposal's five "Key Issues", in gist:**
  1. whether the current computerized inventory system suits all parts of the business;
  2. what inventory investment is needed to meet service objectives under current systems;
  3. whether centralized inventories are cost-effective;
  4. what the current levels of obsolete and slow-moving stock are;
  5. how much inventory turn could improve with policy, organization and system changes.
- **Diagnosis.** Minto calls the list verbose and unattractive, a poor way of expressing a business message. It is hard to penetrate because the author had no clear picture to convey, and that lack itself stemmed from muddled problem solving.
- **Test 1: are these really issues?** An issue, properly, is a question that only yes or no can answer. Framing it that way aims the analysis at the precise output that would confirm or refute your account of the causes.
  - "What level of inventory investment is necessary?" is not an issue. Recast as issues: "Is today's stock level excessive?" or "Do we really need all the inventory we carry?"
  - Both recastings are really ways of fixing the success criterion, i.e., R2.
- **Re-define the problem:**
  - Opening Scene: map of Texas with a $27m central hub and spokes to regional warehouses.
  - Disturbing Event: the new owners believe $27m is excessive.
  - R1 = too much capital locked in stock. R2 = an appropriate amount of capital in stock.
  - Settle the target figure first; only then can you tell whether the current figure is really excessive.
- **Tree of causes,** assuming the figure is too high: High cost of inventory → order too much / keep too long.
- **Proper issues** follow from it (they correspond loosely to original points 2 and 4):
  - Does the central system order correctly?
  - Does it hold excess obsolete or slow-moving stock?
- **Lesson.** The "issues" label misleads. The list is really describing the *steps the consultant will take* to fix the client's problem, which is that centralization locks up too much working capital in stock. A better framing:
  ```
  We will determine whether/how you can cut the cost of inventory
  ├─ Determine the "right" level of inventory to meet customer-service objectives with the present centralized structure
  ├─ Determine how much the present level can be lowered by changing procedures
  └─ Determine whether the inventory level can be lowered further by decentralizing the structure
  ```
- **Minto's general position:**
  - An "Issues" section is never necessary, and least of all in a proposal. Whatever issues exist fall out of the analytical method chosen, so **issues, analytical process and study deliverables collapse into one and the same thing**.
  - She considers issue-based thinking unproductive in every case.
- **Energy example: ten "Major Issues"**, in effect questions about ways to cut factory energy cost.
  - In gist:
    1. savings from better operating practice and low-capital projects in each mill;
    2. resulting cost advantage vs competitors and its sustainability;
    3. competitive lead from a focused capital program;
    4. the right energy R&D/engineering programs;
    5. best fuel mix and sourcing;
    6. whether capital-project approval surfaces the best energy projects;
    7. influencing government funding, taxation and regulation;
    8. human resources to manage energy tasks;
    9. competitive penalty from product/mill assignments;
    10. corporate energy strategy and business plan.
  - Diagramming the alternative ways to cut energy cost gives a choice diagram (**Exhibit 50**), with issue numbers attached:
  ```
  Cut energy costs  [10]
  ├─ Cut BTUs used
  │   ├─ Fix existing equipment to use less: repair/maintain · insulate · modify   [1, 2, 6]
  │   └─ Create new equipment to use less: buy · design                          [3, 4]
  └─ Cut cost of each BTU
      ├─ Use lower-cost fuels in existing equipment                              [5]
      └─ Add new equipment that uses less costly fuel                            [3]
  ```
  - Mapping result: issues 7, 8 and 9 don't relate to the subject at all. Issues 1, 2 and 6 concern fixing existing equipment; 3 and 4 concern creating new equipment; 5 concerns cheaper fuels in existing equipment. Adding new equipment that burns cheaper fuel is touched on only in 3. Issue 10 refers to cutting energy costs as a whole.
- **Principle.** Any grouping of ideas must originate in some analytical act of thought. When solving a problem, that act was most likely one of the analysis structures you built. **Checking ideas against those structures is a way to confirm their logic holds.**

### Performing an Issue Analysis (p. 163)
- Some people call the building of diagnostic frameworks "Issue Analysis". But the label gets stretched, loosely, to cover nearly any logic tree, leaving practitioners unsure how to use either kind. Minto sets out where the confusions lie.
- **The word "issue."**
  - In the strict sense, an issue is a question worded so that only yes or no can answer it. The term is borrowed from the legal "at issue": two opposing positions, of which only one prevails.
  - An open "how should we reorganize?" has nothing at issue. "Should we adopt a functional organization?" does, and asking it signals that the thinking has reached a point of decision.
- **Why it matters.** Yes/no questions matter because they produce clean answers. How well a team can frame such questions determines how efficiently it solves problems.
- **Vocabulary fix.** Use **"concerns"** for lists of topics that show what worries the client, and keep **"issues"** for yes/no questions.

### The History (pp. 163–165)
- **Origin.** As far as Minto can tell, the term was invented at McKinsey by David Hertz and Carter Bales during 1960s work for New York City (under Mayor Lindsay). The method analysed decisions in complicated settings, drawing on systems-analysis ideas then current at the U.S. Department of Defense.
- **Purpose.** It aimed to help city officials see their options clearly and feel sure their choices were rational in situations where:
  - a decision was pressing (e.g., the volume of subsidized middle-income housing to supply);
  - several options had merit;
  - many variables and objectives were in play;
  - outcomes could be judged on multiple criteria that often pulled against each other;
  - the chosen course could significantly affect other decision areas.
- **Example.** New York could provide middle-income housing in various ways (one location, several), but any of them might conflict with objectives in other policy areas (refuse disposal, air pollution). Issue Analysis was a way to balance those objectives.
- **Method:**
  1. Draw a chronological diagram of the policy area showing the **Major Decision Variables (MDVs)** at each stage: environmental, economic, administrative and social factors affecting each activity.
  2. Formulate hypotheses on how the MDVs would affect performance against objectives.
  3. Define the decisions to be made in terms of the MDVs judged essential to meeting the objectives.
- **Exhibit 51, middle-income housing system with MDVs marked:**
  - Site (site availability) and Sponsor (developer motivations) → Approval process (accept or reject; how much tax exemption; how much other subsidy) → Relocation (number of families; alternative housing options) → Site preparation (site characteristics; labor; materials and other costs) → Construction (site characteristics; labor; materials and other costs) → Marketing (location; rent; marketing effort; market forces) → Occupancy (tenant selection policies; market forces).
  - Taking one MDV: tenant selection policy directly affects the number of housing applications, which affects how many units the city should consider building. So it is a key decision tied to the housing "issue" and has to be assessed against feasible alternatives using a standard form.
- **Exhibit 52, standard assessment form:**
  - Left side, "perspective on the issue": performance against objectives; program need; key performance determinants; available resources; interrelationships; public opinion; other factors.
  - Right side, "analysis of the issue": the issue → decision areas (Decisions 1–3) → alternatives per decision → projected consequences scored against objectives A–E and criteria A–E, with weighting factors, impact and ranking.
- **Fate.** The technique was far too complex for ordinary people to use and was dropped. But the ideas of mapping the physical system and forming hypotheses stuck. Now almost any analytical framework gets called "Issue Analysis" and is described as crucial to problem solving and teamwork. As consultants move between firms, the explanations of how to do it carry some of the original confusion with them.

### The Misconceptions (pp. 166–167)
- Minto knows of no firm using Issue Analysis effectively; everyone whose process she knows has it somewhat muddled.
- **UK retail bank illustration:**
  - Opening Scene: UK retail bank | European retail banking structure.
  - Disturbing Event: the EC lets banks operate across borders.
  - R1 = opportunity to operate in other European countries. R2 = build a profitable position in Europe. Between them: develop a strategy for retail banking in Europe.
- **The firm's taught "Issue Analysis" steps:**
  1. Start with the client's question (e.g., what should our European strategy be?).
  2. Formulate issues and sub-issues (questions answerable yes/no).
  3. Devise hypotheses (likely answers to those questions).
  4. Identify the data needed.
  5. Assign responsibility, etc.
  6. Draw conclusions and develop recommendations.
  7. Check the validity of conclusions and recommendations.
- This looks close to the approach Minto recommends, but it contains several misunderstandings that frustrate young consultants trying to copy it:
  1. **Wrong source of issues.** Issues can't be derived from what the client asks, since that question (as here) typically expresses an R2. Their source has to be **the structure of the situation that produced R1**: in this case, how the bank's business is built and how well it fits European retail banking.
  2. **Unexplained leap.** Nothing says where the issues and sub-issues come from, or how to judge whether the list is collectively exhaustive.
  3. **Issues vs hypotheses confusion.**
     - Making "hypothesis" a deliberate third step is unnecessary; it makes no difference to the analysis whether you hypothesize yes or no.
     - If anything, issues come *from* hypotheses, since building the framework already hypothesizes that the problem lies within it. No insight is gained from the distinction.
     - Working in issues and sub-issues is simpler, because a single analytical tree generates or implies all of them.
  4. **Tree-type confusion.** Firms also apply the "Issue Analysis" label to option-generating logic trees and to trees that project the consequences of those options. Generating alternatives with logic trees is legitimate. But calling it Issue Analysis confuses things, because these trees differ in type from diagnostic frameworks.

### Closing: the dual function (p. 167)
- All the Part Three techniques (problem definition, diagnostic frameworks, logic trees) do two jobs:
  1. They make problem solving systematic: attention stays on what is truly wrong for the client, every cause gets surfaced, and the solutions stay relevant.
  2. They greatly reduce the effort of organizing and communicating your thinking in the final report.
- Your conclusions and recommendations have to rest on the logic these structures supply, and little work is needed to reshape that logic into a pyramid.
- When a consulting report is laborious to produce and still comes out muddy, the usual reason is that the clarifying thinking came too late in the project.

### How the analysis outputs flow into a pyramid (synthesis of pp. 120, 122, 150, 156–162, 167)
- **Introduction.** The problem definition (Opening Scene, Disturbing Event, R1, R2) answers "is there a problem / where?" and becomes the S-C-Q (`07-defining-the-problem.md`).
- **Causes.** The diagnostic framework, worked through its yes/no questions, establishes *why* the problem exists. The confirmed branches become the findings that support the recommendations.
- **Actions.** The logic tree of possible solutions, filtered by benefit and risk against R2, yields the recommended set of actions. These become the Key Line (steps/changes), e.g., Exhibit 36's capacity steps.
- **Proposals.** In a proposal, the pyramid is the analytical process itself (e.g., "We will determine whether/how you can cut inventory cost" over three "Determine…" steps), not a list of "issues".
- **Client explanation.** The framework itself can be shown as today / what you must have been doing / ideal.
- **Validation.** Any grouping in the draft can be checked against the tree it came from (Exhibit 50). Items that map nowhere are irrelevant; branches with no item are gaps.

> **Skill note:** The book does not give a single step-by-step "tree to pyramid" conversion; the bullets above assemble what it says in several places. A storyboarding skill can treat the confirmed cause branches as supporting evidence and the chosen logic-tree branches as the Key Line.

## Rules
- **ANL-1**: Structure the analysis before gathering data; never collect whatever is available and postpone thinking. *Why:* data-first wastes effort (one firm estimated 60%), leaves gaps behind major recommendations, and makes writing painful. *Check:* does every planned data item trace to a question in a framework drawn beforehand? (pp. 140–142)
- **ANL-2**: Derive likely causes (hypotheses) from the structure of the Opening Scene, the situation that produced R1, not from thin air and not from the client's question (which states R2). *Why:* only the structure gives a principled, checkable source of causes. *Check:* is each hypothesis attached to an element of the drawn structure? (pp. 142, 166)
- **ANL-3**: Keep diagnostic frameworks (find causes), logic trees (generate or evaluate solutions) and decision trees/PERT charts (plan action) distinct, and use each for its own job. *Why:* lumping them as "Issue Analysis" or "analytical techniques" causes misuse. *Check:* can you say which kind each chart is and which Sequential Analysis step it serves? (pp. 142, 150, 167)
- **ANL-4**: Build diagnostic frameworks using one or more of the three structuring methods: divide (physical structure), trace cause and effect (financial, task or activity structure), or classify (causes, choice structures). *Why:* these are the only ways to impose structure. *Check:* name the method behind each framework. (p. 143)
- **ANL-5**: Make each level of a diagnostic tree MECE, especially the top branches. *Why:* the upper classification guides generation of lower causes and guarantees completeness. *Check:* do sibling branches overlap? Does anything that could cause the effect fall outside them? (pp. 143, 148–149)
- **ANL-6**: Convert every branch into a yes/no question, and plan data gathering by asking what must be learned to answer each one yes or no. *Why:* yes/no answers identify or exclude causes unambiguously and tell you in advance when research is done. *Check:* is each data request tied to a specific yes/no question? (pp. 145, 149–150, 156)
- **ANL-7**: Test candidate causes in order of ease of elimination, and use industry experience to choose where to look first. *Why:* cheap eliminations come before expensive tests (no brain scan for a sinus headache). *Check:* is the test sequence justified by cost or likelihood? (pp. 143, 148)
- **ANL-8**: For a physical-structure framework, draw the system's units and flows in their actual or intended working state, and read the questions off the picture. *Why:* the picture reveals where breakdowns could occur. *Check:* the framework shows units, flows and the point where R1 shows up. (pp. 143–144)
- **ANL-9**: Quantify a financial-structure tree (put numbers on nodes) to locate where the shortfall arises before drilling down. *Why:* numbers quickly show whether sales, costs or both drive R1. *Check:* nodes carry figures or comparisons. (p. 145)
- **ANL-10**: In a task structure, phrase every node as a managerial task (Increase…/Reduce…), working down from EPS through the P&L and balance sheet. *Why:* a problem found at a node then already names the needed action. *Check:* every node starts with an action verb. (pp. 146–147)
- **ANL-11**: For an activity structure, start from the undesirable effect, hypothesize the MECE reasons at the next level, and keep asking "why would this happen?" until you reach gatherable facts. *Why:* this gives a complete list of areas where facts can be gathered. *Check:* the tree's leaves are observable, measurable conditions. (pp. 147–148)
- **ANL-12**: In a choice structure, mirror the real sequential process with dual (either/or) forks, and in sequential structures fix upstream (left) weaknesses before downstream (right) ones. *Why:* later stages can't perform if earlier ones are broken (no point boosting use frequency before fixing promotion and targeting). *Check:* do forks follow the process order, and are recommendations sequenced left to right? (pp. 149–150)
- **ANL-13**: If no line of inquiry in a sequential marketing structure reveals the problem's source, go back and recheck the definitions of target market and consumer benefit. *Why:* the whole structure rests on those definitions. *Check:* a "no cause found" outcome triggers re-examination of the foundational definitions. (p. 151)
- **ANL-14**: Choose which frameworks to build from the Opening Scene of the problem definition, and decide depth using subject-matter knowledge. *Why:* the Opening Scene implies where causes can lie, and there is no substitute for knowing the field. *Check:* does each framework model part of the Opening Scene? (p. 153)
- **ANL-15**: Gather first only the data needed to draw the diagnostic framework; then form hypotheses; then gather only the data that proves or disproves them. *Why:* broad interviewing produces more data than can be absorbed, with no objective test of relevance. *Check:* the work plan has a framework-building phase before hypothesis-testing data collection. (p. 154)
- **ANL-16**: Before fieldwork, identify each data item's source, owner, schedule and cost. *Why:* a question-driven plan makes the effort administratively predictable. *Check:* the data plan lists these four attributes per item. (p. 156)
- **ANL-17**: Use a logic tree to lay out the MECE set of possible actions (or strategic opportunities), then weigh each option's payoff against its risk to choose the final set. *Why:* systematic breakdown surfaces options intuition misses, and evaluation picks among them. *Check:* do the recommended actions come from an exhaustive option tree with stated benefit and risk? (pp. 156–158)
- **ANL-18**: Test any grouped list in a draft (issues, findings, recommendations) by mapping each item onto the analytical tree it should come from; drop items that don't map and look for empty branches. *Why:* every grouping must come from an analytical activity, and mapping exposes irrelevance, overlap and gaps. *Check:* every item has a branch; every important branch has an item. (pp. 159–162)
- **ANL-19**: Reserve "issue" for questions answerable yes or no; call topic lists "concerns"; rephrase open questions ("What level is needed?") as yes/no issues ("Is the present level too high?"). *Why:* only yes/no questions direct analysis to a specific end product. *Check:* every listed "issue" is a yes/no question. (pp. 160, 163)
- **ANL-20**: Before judging whether R1 really holds, establish the R2 benchmark (e.g., the "right" inventory level). *Why:* you can't call a figure too high without knowing what it should be. *Check:* the plan's first analytical step pins down R2. (p. 160)
- **ANL-21**: Don't write an "Issues" section in a proposal; present the analytical process and its end products as the pyramid. *Why:* issues, method and deliverables coincide, so a separate issues list only muddies the message. *Check:* the proposal's body is a process pyramid, not a question list. (p. 161)
- **ANL-22**: Don't treat "devise hypotheses" as a separate step from formulating yes/no issues; derive both from the same analytical tree. *Why:* hypothesizing yes or no changes nothing in the analysis, and the separation adds confusion. *Check:* the plan has one tree whose nodes are the questions. (pp. 166–167)
- **ANL-23**: Use a completed diagnostic framework to explain the situation to the client in three views: today, what must logically have been happening, and the ideal. *Why:* comparison with the ideal demonstrates the need for change and exposes weaknesses. *Check:* client-facing material shows actual vs ideal structures. (p. 150)
- **ANL-24**: Make the analytical structures the backbone of the final pyramid: definition → introduction; confirmed causes → support; chosen actions → Key Line. *Why:* the logical structures must underlie conclusions and recommendations and convert to pyramid form with minimal effort. *Check:* each Key Line point traces to a branch of a framework or logic tree. (p. 167)

## Procedures

### P1. Structure an analysis end to end
1. **Start from the problem definition** (`07-defining-the-problem.md`): Opening Scene, Disturbing Event, R1, R2. If R2 is not yet a measurable benchmark, make establishing it the first analytical task. (ANL-20)
2. **Pick the framework type(s) from the Opening Scene.** (ANL-14)
   - Opening Scene is a physical system (distribution chain, plant flow, industry chain) → **physical structure** (P2).
   - R1 is a financial result (low ROI, low EPS) → **financial structure**; if you want the nodes to read as actions → **task structure** (P3).
   - R1 is an operational outcome (overlong installs, high cost) → **activity structure** (P4).
   - Causes can be pre-grouped by similarity, or the process is a sequence of either/or stages → **classification / choice / sequential structure** (P5).
3. **Gather only the data needed to draw the framework.** Use subject knowledge to decide how deep to go. (ANL-15)
4. **Make each level MECE**; reorganize the top branch until it is. (ANL-5)
5. **Turn branches into yes/no questions.** For each: "If this were the weakness, what exactly would I expect to find?" (ANL-6)
6. **Order the tests** by ease of elimination, likelihood (from experience), and process order (upstream first). (ANL-7, ANL-12)
7. **Write the data plan**: for each question, the data that answers it yes/no, plus source, owner, schedule and cost. (ANL-16)
8. **Gather and answer.** Prune excluded branches and drill into confirmed ones. *Decision:* if nothing is confirmed, revisit the framework's foundational definitions (e.g., target market and consumer benefit) or the problem definition. (ANL-13)
9. **Generate solutions** for confirmed causes with a logic tree (P6). Evaluate benefit and risk against R2. (ANL-17)
10. **Build the pyramid** (P8). (ANL-24)

### P2. Physical-structure framework
1. Draw the units (organizations, stages, facilities) and the flows between them, as the system is or should be.
2. Mark where R1 shows up (e.g., share of market at the consumer).
3. For each unit or flow, ask: could a failure here produce R1? Phrase it as yes/no ("Do we fail to make customers aware?").
4. For an industry map, segment the industry, then note for each segment volume, competitive structure, value-added points, cost behaviour, profit pools and their sensitivity, and asset commitments. Mark economic and market points of leverage, then gather data at those points to find vulnerabilities.

### P3. Financial / task structure
1. Put the top financial measure at the root (ROI, or EPS for a task tree).
2. Split it by its arithmetic components (profit vs assets; sales vs costs; variable vs fixed…), then each component into its key influences, then into their elements.
3. *Task variant:* rewrite each node as a managerial task ("Increase Net Sales", "Reduce Leaf"), overlaying P&L and balance-sheet line items.
4. Put numbers on the nodes: trends, comparisons with last year, industry and competitors, sensitivities.
5. Ask yes/no at each node ("Is the problem in product volume? In pricing?") and list the data needed to answer each.
6. Use the findings to set priorities among the tasks.

### P4. Activity structure
1. Root = the undesirable effect, stated concretely ("Installations take longer than expected").
2. Visualize every party and activity involved (e.g., factory, installers, facilities, equipment, testers, customer approvals).
3. Level 2: hypothesize the MECE ways the effect could arise. Often these follow an arithmetic identity (men × hours per man × hours on duty).
4. For each, ask "what could cause this?" and branch again (pace / time required / delays), repeating until the leaves are observable conditions.
5. Use experience to pick where to start gathering facts.

### P5. Classification, choice and sequential structures
1. *Classification:* group candidate culprits by similarity under a MECE top split (e.g., Sales: semi-fixed vs variable factors; gross margin; costs). Assume each group may be at fault, and specify the information that would prove each culprit guilty. Then phrase yes/no questions.
2. *Choice:* write the sequential process (e.g., choose store → call → act → act well). At each stage fork into right/wrong (or effective/ineffective). Stop forking a "wrong" branch, since that is the cause. Keep forking the "right" branch until you reach precise likely causes.
3. *Sequential (Holland):* answer in order (1) Is there a problem? (measures), (2) Where? (region, channel, pack, consumer type), (3) Why? Then go through the stages left to right: positioning → distribution → awareness → trial → repurchase. Recommend fixes for left-hand weaknesses before right-hand ones. If no stage reveals a cause, recheck target market and consumer benefit.

### P6. Generate solutions with a logic tree
1. Root = the action objective for a confirmed cause (e.g., "Reduce direct labor costs") or the strategic aim (e.g., "Capitalize on opportunities from economic growth").
2. Break it down MECE: first into cost elements or departments, then using any arithmetic identity (cost/hour × hours/unit), then into the concrete levers for each factor.
3. Continue to the level where actions are specific.
4. For each leaf action, estimate payoff and risk; choose the recommended set.
5. For strategic opportunities, also note what each would require. Push for collective exhaustiveness.

### P7. Audit a grouped list (e.g., "Key Issues") with a logic tree
1. Restate the problem with the framework (Opening Scene, Disturbing Event, R1, R2). Note whether any item is really an attempt to define R2.
2. Check each item: is it a yes/no question? If not, rephrase it ("What level is necessary?" → "Is the present level too high?"). If it is just a topic, call it a concern.
3. Build the tree of causes (diagnostic) or of ways to reach R2 (logic tree) that the list should be covering, e.g., "High inventory cost → order too much / keep too long" or "Cut energy costs → cut BTUs used / cut cost per BTU …".
4. Tag each list item with the branch number it addresses.
5. Items that map to no branch are off-subject: drop them. Branches with no item are gaps: add them. Items scattered across levels signal muddled thinking: regroup by branch.
6. Rewrite the section as the process or end products, e.g., a "We will determine…" pyramid, rather than an "Issues" list. (ANL-18, ANL-19, ANL-21)

### P8. Convert the analysis into a pyramid
1. Introduction: S-C-Q from the problem definition (`07-defining-the-problem.md`, P3).
2. Top point: the answer to Q, e.g., the recommended action set or the strategy, or for a proposal, what the study will determine.
3. Key Line:
   - Report: the chosen actions from the logic tree (steps/changes), grouped and ordered (`05-logical-order.md`).
   - Proposal: the analytical process steps, one per main framework branch.
4. Support beneath each action: the confirmed causes (yes answers) from the diagnostic framework, plus the benefit/risk evidence.
5. Validate each grouping by mapping it back to its tree (P7).
6. Optionally include the framework diagrams as exhibits that show the client today vs ideal. (ANL-23, ANL-24)

## Templates and patterns

**Diagnostic tree skeleton (generic)**
```
<Undesired result R1, stated concretely>
├─ <MECE cause class A>
│   ├─ <sub-cause A1>   → Q: Is A1 occurring? (data: …, source: …, owner: …, by: …, cost: …)
│   └─ <sub-cause A2>   → Q: …
└─ <MECE cause class B>
    ├─ <sub-cause B1>   → Q: …
    └─ <sub-cause B2>   → Q: …
```

**Arithmetic split pattern (activity / logic tree)**
```
<Total> = <factor 1> × <factor 2> × <factor 3>
<Total too high/low>
├─ <factor 1 off>
├─ <factor 2 off>
└─ <factor 3 off>
e.g., Cost/cigarette = Cost/hour × Hours/cigarette;  Install time ← men/rack, man-hours/rack, hours on duty/week
```

**Choice (dual-fork) structure**
```
<Ineffective X>
├─ <wrong at stage 1>  ✗ cause
└─ <right at stage 1>
    ├─ <wrong at stage 2>  ✗ cause
    └─ <right at stage 2>
        └─ … until precise causes: <c1> · <c2> · <c3>
```

**Sequential diagnostic (Holland pattern)**
```
1 Is there a problem? (measures)   2 Where? (segments)   3 Why? stage1 → stage2 → stage3 → stage4 → stage5
Rule: fix leftmost weak stage first.  Feedback: if no stage fails, recheck foundational definitions.
```

**Yes/no question frames**
```
Is <element> causing <R1>?
Do/Does <unit> <perform function> as required?          (e.g., Do they deliver lead times as promised?)
Is <measure> <too high/too low> compared with <benchmark>?
Are <controls in area A> raising <costs in area B>?
```

**Concern → issue conversion**
```
Concern / open question:  "What level of <X> is necessary?"   "How should we <act>?"
Issue (yes/no):           "Is the present level of <X> too high?"   "Should we <act in a specific way>?"
```

**Data plan row**
```
| Yes/no question | Data needed | Source | Responsible | Schedule | Est. cost |
```

**Proposal pyramid (process, not issues)**
```
We will determine whether/how you can <reach R2>
├─ Determine the "right" <R2 benchmark> under the present <structure>
├─ Determine how much <measure> can be improved by changing <procedures>
└─ Determine whether <measure> can be improved further by changing <structure>
```

**Client explanation triad (p. 150)**
```
1 Current:  how the system runs today, producing R1
2 Implied:  what the system logically had to be doing to produce R1
3 Ideal:    how the system must look to produce R2 (the to-do)
```

## Worked examples
**Headache (p. 143).**
- Before: unexplained pain, no basis for treatment.
- After: physical (external: bump, allergies, weather sinus; internal: flu, tumor, water on brain) vs mental (stress, hypochondria).
- Lesson: a MECE classification lets you test the cheapest-to-eliminate causes first.

**Exhibit 37 (p. 144): falling share of market for a retailer.**
- After: manufacturer → wholesaler → retailer → consumer, with marketing (awareness → initial purchase → repurchase) and sales (shelving → pricing → special merchandise support) paths.
- Lesson: each box becomes a yes/no question ("Are we failing to make customers aware?").

**Exhibit 38 (p. 144): industry structure.**
- After: value chain from raw material to post-purchase services, with economic and market points of leverage marked.
- Lesson: segment the industry and locate value, cost, profit and asset concentration to find vulnerabilities.

**Exhibit 39 (p. 145): low ROI.**
- After: ROI → trading profit (sales: prices, products, service, market; costs: variable labor/services/materials, fixed) and assets (net current, fixed).
- Lesson: put numbers on it to see whether sales, costs or both drive R1, then ask yes/no node by node.

**Exhibit 40 (pp. 146–147): cigarette company EPS task tree.**
- After: Increase EPS → increase trading profits & assets (tobacco/non-tobacco; contribution; oncost; trading assets) and increase financial gearing (interest, tax, sale/leaseback). Leaves are verb-phrased P&L and balance-sheet tasks.
- Lesson: task phrasing makes the needed action evident wherever the problem is found.

**Exhibit 41 (pp. 147–148): telephone-switch installations overrunning.**
- After: fewer hours on duty / fewer men per rack / more man-hours per rack → slower pace, more time required, unexpected delays → detailed causes.
- Lesson: MECE "why" levels give a complete map of where to gather facts.

**Exhibit 42 (pp. 148–149): retail profits down.**
- After: sales (semi-fixed vs variable), gross margin, costs.
- Lesson: a MECE upper classification guides generation of lower causes and the proof data for each.

**Exhibit 43 (pp. 149–150): ineffective sales support.**
- After: HQ vs retail → right/wrong stores → right/wrong frequency → right/wrong activities → effective/ineffective → specific causes.
- Lesson: mirror the selling sequence in either/or forks.

**Exhibit 44 (pp. 150–151): brand diagnosis (Holland).**
- After: Problem? → Where? → Why? (positioning → distribution → awareness → trial → repurchase), with a feedback loop to target market and consumer benefit.
- Lesson: complete and ordered; fix the left before the right.

**Exhibit 45 (p. 152): decision tree and PERT chart.**
- Lesson: these show the need for action, not questions; they are not diagnostic frameworks.

**Exhibits 46–47 (pp. 153–156): Barrows ISD falling behind on orders.**
- Before: a proposal to gather eight broad categories of data by interviewing.
- After: draw the factory flow (order processing, engineering, purchasing, material control, scheduling, dispatching, evaluation); hypothesize weak points; ask six yes/no questions (lead times, purchased items, stock availability, capacity, system costs, management reports); plan data with sources, owners, schedule and cost.
- Lesson: framework first, then hypotheses, then only proof/disproof data.

**Exhibit 48 (pp. 157–158): cutting labor cost in cigarette making.**
- After: departments → cost/hour × hours/million → overtime, cheaper labor, wage awards / people per machine, machine speed, machine efficiency.
- Lesson: an exhaustive action tree, then benefit and risk per action, gives the recommended set.

**Exhibit 49 (p. 158): bank growth opportunities.**
- After: five MECE opportunity branches with requirements beneath.
- Lesson: logic trees also lay out strategic options.

**Texas inventory "Key Issues" (pp. 159–161).**
- Before: five wordy, mixed questions.
- After: R1 excess capital in inventory vs R2 the right amount; cause tree order too much / keep too long; two yes/no issues; a proposal pyramid of three "Determine…" steps under "We will determine whether/how you can cut the cost of inventory."
- Lesson: an "issues" list is really the study process; restate it as such.

**Exhibit 50 (pp. 161–162): ten energy "Major Issues".**
- After: cut BTUs (fix existing equipment / create new) vs cut cost per BTU (cheaper fuel in existing equipment / new equipment for cheaper fuel). Issues 7–9 map nowhere; 1, 2, 6 / 3, 4 / 5 / 3 / 10 map to branches.

**Exhibits 51–52 (pp. 164–165): NYC middle-income housing (original Issue Analysis).**

- Lesson: the origin of mapping the system and hypothesizing; too complex, so it was abandoned.

**UK retail bank (p. 166).**
- Problem: EC opens cross-border banking; R1 opportunity; R2 profitable European position. The firm's 7-step "Issue Analysis" starts from the client's question.
- Lesson: issues must come from the structure (bank vs European banking structure), not from the R2-type question; hypotheses are not a separate step.

## Nuances and exceptions
- **Data-first isn't impossible**, just always more work (p. 140). Historically it made sense when firms lacked industry knowledge (p. 141).
- **Subject knowledge is a precondition.** The frameworks don't replace deep knowledge of the field. Creative solutions come mainly from people steeped in the subject; logic trees are a support for those without that depth (pp. 153, 156).
- **Partial frameworks are fine.** How much of a framework to work through depends on what you already know (p. 153). Exhibit 47 is explicitly a *partial* flow diagram.
- **The three structuring methods.** Minto says Ch 6 established that there are only three ways to structure anything: divide, trace cause and effect, classify (p. 143). This matches Ch 6's three analytical activities in `05-logical-order.md`: dividing a whole maps to structural order, tracing causes of an effect to time order, and classifying to degree order.
- **The choice structure is "related to" the activity structure** (both seek causes of an undesirable effect) but is presented under classification (p. 149).
- **Yes/no questions as crucial experiments.** They play the role that experiments play in science, and they define in advance when the research is finished (p. 150). See `09-abduction.md` for the scientific counterpart.
- **Diagnostic frameworks double as client communication** (p. 150), not just internal tools.
- **On "issues".** Minto is not against yes/no questions (she calls them vital). She opposes (a) using "issue" loosely, (b) "Issues" sections in proposals, and (c) deriving issues from the client's question (pp. 161, 163, 166).
- **"Issue Analysis" in its original form** was a heavyweight decision-analysis method for complex public-policy choices. Today's usage is a loose descendant (pp. 163–165).
- **Book inconsistencies to be aware of:**
  - p. 157 says the costly item was "indirect labor", but Exhibit 48's root is "Reduce direct labor costs".
  - p. 156 says the dropped data items formed the basis of "the diagram shown in Exhibit 46"; the flow diagram is Exhibit 47.
  - The OCR shows "ISO", but the exhibit reads "ISD" (Information Systems Division).
- **The Exhibit 44 feedback rule** is specific to the brand diagnostic.

> **Skill note:** The feedback rule generalizes naturally to "if no branch confirms, re-examine the root definitions or the problem definition". That generalization is an interpretation, not a statement in the book.
